# Agent 工具规范

状态：当前规范（规范版本）  
最后验证：2026-08-23

## 所有权边界

Dayboard 负责调度语义、持久化、授权和模型可见的业务工具。
North 负责通用 Agent 循环和中间件执行。模型提出业务字段；运行时注入可信上下文，服务端验证每项操作。

模型绝不会接收或提供 `user_id`、`run_id`、`operation_key`、
`*_by_run_id`、permissions 或可信默认时区。Local datetime 字段不带偏移，并使用 `UserContext.timezone` 解析。当前不支持明确的外国时区输入，也不会进入模型可见 schema。

调度回执暴露整数 `row_version`；变更要求 `expected_row_version` 以实现原子乐观锁。审计时间戳不是模型可见的并发令牌。

## 模型可见面

Dayboard 暴露七个调度工具：

| 领域 | 工具 | 职责 |
| --- | --- | --- |
| 日历 | `create_calendar_entry` | 创建一项已调度活动并返回内部冲突结果。 |
| 日历 | `search_calendar_entries` | 列出或搜索日历条目，并回答重叠/可用性查询。 |
| 日历 | `reschedule_calendar_entry` | 移动一个选定条目并返回内部冲突结果。 |
| 日历 | `cancel_calendar_entry` | 取消一个选定条目但不硬删除。 |
| 任务 | `create_task_item` | 创建一个没有可解析日期或时间的 open 任务。 |
| 任务 | `search_task_items` | 按可选标题和状态列出或搜索任务。 |
| 任务 | `update_task_item` | 重命名、完成或取消一个选定任务。 |

`ask_clarification` 是运行时交互工具，而非调度业务工具。它在每个活动工具集中都保持对模型可见，使歧义选择和缺少必需数据的情况能够使用可恢复交互协议。因此，初始模型可见面总计为八个工具。

没有单独的列表工具。空搜索查询执行有界列表操作。日历搜索接受可选的本地时间区间；省略时服务端应用已记录的默认窗口。其区间谓词使用重叠语义，因此在查询开始前启动但在查询区间内结束的条目仍会返回。结果必须具有服务端最大数量限制和确定性排序。

不存在模型可见的冲突检查工具。日历创建和重新安排在应用服务内部检查冲突。可用性问题使用带请求区间的 `search_calendar_entries`。

搜索工具不接受 `purpose`。搜索负责识别对象；后续变更工具才是权威操作。进度文本保持中性，交互状态根据实际的变更/澄清流程派生，而不是根据模型提供的搜索标签派生。

新任务状态不可由模型选择。`create_task_item` 始终创建 `open` 状态；状态变更使用 `update_task_item`。

分类有意保持机械性：任何可解析的日期、时刻或时段都会创建日历条目，即使措辞描述的是完成事项或截止时间。日历条目有两种明确的时间模式：

- `timed` 存储解析为某个时刻的本地时钟时间。没有时刻的时段只有在操作已被分类为日历条目后，才使用其确定性默认值。
- `anytime` 只存储本地日历日期。诸如 `明天提交报告` 的仅日期表达式使用此模式；系统不得臆造 `00:00`、`09:00` 或其他隐藏时刻。

anytime 条目没有开始/结束时刻或提醒，也不参与时钟重叠冲突检查。日历搜索按其本地日期包含该条目，并渲染为 `随时`。任务没有模型可见的日期或时间字段，专用于没有可解析时间锚点的操作，包括 `晚点`、`有空` 和 `抽空` 等模糊表达。

## 输入与结果形状

Schema 只包含识别或执行操作所需的字段。字段描述负责格式约束；系统提示词负责跨工具调度策略。避免在两处重复同一策略。

模型可见的写入结果包含：

- 稳定的结果 `type`；
- 权威日历条目或任务对象；
- 日历创建或重新安排可能产生的冲突；
- 仅当实体中无法明显看出新增信息时才提供可选的简洁 `summary`。

模型可见结果是 `ToolMessage.content` 中的紧凑回执。完整且安全的实体快照单独放在 `ToolMessage.artifact` 中，投影为类型化 SSE，并持久化到会话元数据。PostgreSQL 仍是产品状态和可见历史的权威来源；检查点工件只是传输副本。详见
[Agent 上下文与记忆契约](./context-memory.md)。

当权威实体已经包含 `id` 时，不要再返回第二个顶层对象 ID。不要返回 `requires_follow_up=false`；澄清由交互工具表示，而不是由休眠的结果标志表示。内部领域模型可以保留审计和幂等字段，而 Agent 投影只暴露渲染和后续乐观变更所需的字段。

依赖序列的创建在 `create_calendar_entry` 上使用 `anchor_entry_id` 和 `expected_anchor_row_version`。这些字段与直接日期/开始/结束输入互斥。搜索选定一个定时条目后，服务会锁定该用户范围拥有的行，验证其版本和活动状态，从权威 `end_time` 派生新的开始时间，检查冲突，并在同一事务中创建新条目。模型不得将 `end_time` 复制到直接的 `local_start`；否则会重新引入搜索/写入竞态。

## 动态绑定

动态绑定是作用于规范工具消息的确定性中间件。它不会增加模型选择器调用，也不会用关键词分类用户文本。

| 状态 | 绑定工具 |
| --- | --- |
| 首个语义轮次或新的用户轮次 | 七个调度工具加 `ask_clarification` |
| 成功的日历搜索结果 | 四个日历工具加 `ask_clarification` |
| 成功的任务搜索结果 | 三个任务工具加 `ask_clarification` |
| 成功的终态写入结果 | 使用确定性、有依据的完成结果结束 Agent 循环；不要再次调用模型 |
| 同一工具调用批次跨越日历和任务领域 | 在批次解决前保留完整工具面 |
| 错误、格式错误的结果或所需工具不可用 | 恢复完整工具面并进行一次恢复尝试 |

搜索后才进行领域收窄，此时下一项操作已知会留在该领域。日历或任务写入不会进一步收窄到更多写入工具。当尾部工具调用批次中的每个结果都是成功的终态写入时，中间件根据规范回执创建简短的本地化完成结果，并在不再次请求 provider 的情况下结束循环。搜索结果、错误、格式错误的结果、部分完成和未解决的混合批次继续交由模型处理。成功日历写入返回的冲突数量仍会显示在确定性完成结果中。
这样可以避免仅仅因为混合命令恰好先执行了日历写入，就隐藏任务。恢复标记必须阻止无界的恢复/重试循环。

生产缓存测量后，动态绑定仍优于固定 schema 面。使用 `count_tokens_approximately`，完整的七个业务工具加澄清工具面约为 1,554 token，日历子集为 1,224 token，任务子集为 505 token。因此，领域收窄使日历搜索后避免重新发送约 330 token，使任务搜索后避免重新发送 1,049 token。一次预热的生产 Eval 在初始完整工具面和收窄后的日历工具面复用了同一个 6,656 token 的提供商提示词缓存前缀，因此每轮固定所有工具没有测得的缓存优势。只有在提供商测量显示 schema 稳定性节省的 token 多于收窄工具面移除的 token 时，才重新审视该决策。

## 验收规范

测试必须证明：

1. 组装的调度工具恰好为七个，可信字段绝不进入其 schema。
2. `ask_clarification` 在完整工具集和领域专用工具集中都保持可用。
3. 空搜索有界，日历区间搜索能够检测重叠。
4. 创建和重新安排在没有独立冲突工具的情况下返回冲突。
5. 创建任务不能选择非 `open` 状态。
6. 变更结果要求并强制执行 `expected_row_version`。
7. 成功搜索会按领域收窄，混合终态写入批次无需再次调用模型即可完成，失败时只恢复一次完整工具面。
8. 流投影和会话卡片渲染权威实体，不产生重复 ID 或 `requires_follow_up` 字段。
9. 仅日期操作创建可搜索的 `anytime` 条目，不包含开始/结束时刻、提醒或时钟冲突；时段操作仍为定时条目。
10. 紧凑回执保持在 token 预算内，完整工件在实时显示和会话刷新后渲染一致。
