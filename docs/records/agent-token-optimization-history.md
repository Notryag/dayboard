# Agent Token 优化历史

状态：只追加的工程记录  
最后审阅：2026-07-27

本文记录每项已测量的 Dayboard Agent token 优化，作为产品和工程亮点。新优化落地时不要替换旧基线。追加新条目时应包含实现、语义验收结果、提供商使用量、缓存行为和已知取舍。提供商报告的使用量是权威数据；离线 `o200k_base` 计数用于比较稳定的系统提示词和序列化的模型可见工具 schema。

当前稳定固定面比初始基线少 1,485 个 token。独立的运行时上下文会为每个请求增加约 67 个动态
token，因此最新一步主要改善了前缀稳定性，而不是实质性减少未缓存输入。在用整数行版本替换
时间戳并发字段后，工具 schema 反而缩小了 18 个 token，尽管新增了 duration 参数。线上输入包含
运行时上下文、提供商协议开销和用户消息，因此不会等于离线固定计数。

## 2026-07-20：事件基线

触发调查的简短调度命令使用了两次模型调用，实际共计 10,362 个 token。两次调用分别消耗了
5,028 和 5,272 个输入 token。在计入消息和协议开销之前，原始稳定输入约由 1,640 个系统提示词
token 及 11 个工具 schema 共 2,077 个 token 组成。已完成的工具载荷也会累积在线程历史中。

该基线暴露出三个相互独立的问题：Northgate 的过期预留导致错误的每日限额拒绝；提示词开头附近
的动态 datetime 阻止了稳定前缀复用；完整固定面又被重新发送用于工具后确认。

## 2026-07-20：稳定前缀、缓存路由与历史边界

运行时日期上下文被移到静态指令之后。Dayboard 增加了稳定且带版本的 32 路
`prompt_cache_key`，并按可信租户/用户身份的哈希进行分区。North 增加了按 token 感知的历史压缩，
阈值为 1,200 个 token、上限为 40 条消息，并标记 summary-model 的使用量。

历史提供商记录曾显示 3,840-5,120 个 token 的缓存读取。变更后的线上温缓存检查显示，11-tool
工具面读取了 4,608 个缓存 token。这证明 OpenAI-compatible 路径和 Northgate 使用量核算可以观测
提供商提示词缓存。

## 2026-07-20：提示词与 schema 压缩

重复的策略文本被合并：系统提示词负责跨工具行为，schema 负责字段约束。固定输入从 3,717 降至
2,694 个 token，减少 27.5%。六个真实无写入语义案例将提供商首轮输入从约 4,710 降至
2,915-2,943 个 token。

第一次压缩后的 Run 暴露出一个真实回归：重新调度搜索了目标日期，而不是原条目的日期。恢复一条
明确的原日期规则修复了该路径。这就是提示词缩减需要线上语义对比，而不能只看 token 数量的原因。

成功的终止写入也开始从最终确认轮移除所有工具 schema。线上合成结果对比将该轮输入从 4,908
降至 3,501 个 token，节省 1,407 个 token。温缓存的无工具变体报告了 3,328 个 token 的缓存读取。

## 2026-07-20：统一的 7+1 工具面与领域绑定

Dayboard 移除了独立的日历/任务列表工具和冲突检查工具。空的有界搜索现在会列出对象，精确的
日历区间使用重叠语义判断可用性，日历写入会在内部检查冲突。搜索 `purpose`、任务创建的
`status`、重复结果 ID 以及恒定的 `requires_follow_up=false` 字段均已移除。可信时区以及
Run/idempotency 字段仍由运行时负责。

初始工具面由七个调度工具加上 `ask_clarification` 组成。成功的搜索会将下一轮模型调用缩小为
对应领域加 clarification；混合领域批次保持完整工具面，终止写入会移除工具，而一次失败结果
会恢复完整工具面，第二次失败则停止工具重试。

固定输入再次从 2,694 降至 2,459 个 token，比上一版本减少 8.7%，比初始基线减少 33.8%。同样
六个线上无写入案例的首轮输入为 2,805-2,814 个 token，并保留了 2,560 个 token 的缓存读取。
真实合成结果的第二轮正确地以 4+1 子集、2,615 个输入 token 选择了日历重新调度，并以 3+1
子集、2,428 个输入 token 选择了任务取消。两者都保留了 `expected_updated_at`；均未执行写入。

## 2026-07-20：绝对时间分类

日历/任务分类被刻意设计为机械规则：任何可解析的日期、时钟时间或时段都会创建日历条目，
包括完成和截止时间措辞。只有没有可解析时间锚点的操作才会成为任务。仅含日期的操作使用已有
的 09:00 日历默认值。

为使 schema 与该规则保持一致，Agent 任务创建现在只接受 `title`；任务更新接受 title 或 status，
且不能添加到期时间。领域的 due 字段仍可供 schedule API 和存储数据使用，但 Agent 不能创建相互
矛盾的定时任务。

固定输入从 2,459 降至 2,202 个 token，本步骤减少 10.5%，比初始基线减少 40.8%。六个真实无写入
案例使用了 2,566-2,573 个输入 token。它们验证了
“明天提交报告”、“明天早上8点前吃药”和“明天买牛奶”会创建日历条目；“提交报告”和
“晚点整理资料”会创建任务；混合消息则会发出两次调用。温缓存请求报告了 2,048 个缓存输入
token。没有执行写入工具。

## 2026-07-20：原生 anytime 日历条目

仅含日期的日历操作现在使用带有 `scheduled_date` 的一等 `anytime` 形状，而不是虚构一个 09:00
时钟时间。时钟/时段操作仍为 `timed`；模糊表达仍会成为无日期任务。Anytime 条目没有时钟提醒，
也不参与重叠冲突判断。

提示词被缩减为语义分类、执行、变更前搜索、澄清和响应规则。持久化默认值与不变量仍保留在
schema 和服务中。提示词从 861 降至 666 个 token。创建 schema 新增了明确的日期/时间联合类型，
使模型可见 schema 增加约 65 个 token，达到 1,406。固定输入因此从 2,202 降至 2,072 个 token，
本步骤减少 5.9%，比初始基线减少 44.3%。提供商输入和缓存读取测量仍待部署后记录。

## 2026-07-22：紧凑工具结果与序列锚点

调度工具现在将每个结果拆分为紧凑的模型可见内容和完整、经过验证的 presentation artifact。该
传输拆分不会改变固定提示词/schema 成本。一个有代表性的生产日历创建载荷从 181 降至 136 个
`o200k_base` token（24.9%），同时保留了后续推理所需的 ID、时间、状态、版本和提醒数据。完整
实体仍可供线上 SSE 和刷新恢复使用，不会进入模型上下文。更广义的 50% ToolMessage-history
目标是在 Run 感知压缩后测量的，并不声称每种单独的回执形状都达到该目标。

跨轮次序列语义随后为日历创建增加了 `anchor_entry_id` 和 `expected_anchor_updated_at`。服务器会
锁定并验证所选条目，并从其权威结束时间推导新的开始时间。提示词成本从 666 增至 772 个 token，
八个模型可见 schema 从 1,406 增至 1,487，固定总量为 2,259。这比上一版本固定面增加 9.0%，但
仍比初始的 3,717-token 基线低 39.2%。新增成本换来了对 `跳完舞蹈去唱歌` 等案例的正确处理，
不会让模型传递过期的结束时间。部署后的提供商和压缩测量记录如下。

部署后的双轮验收创建了一个 09:00-10:00 的跳舞条目，随后搜索该条目，并准确地在 10:00-11:00
创建唱歌条目。第一个 Run 使用两次模型调用，共计 4,468 个输入 token 和 63 个输出 token；其
首轮使用 2,523 个输入 token。带锚点的第二个 Run 需要三次语义调用（搜索、创建、确认），共计
8,370 个输入 token 和 174 个输出 token。它产生了零个摘要事件，消除了之前重复压缩的失败模式。

Northgate 按 Run 关联了全部五个请求。它报告第二个 Run 的第一次调用读取了 1,536 个缓存提示词
token。提供商在其他四次调用中省略了缓存 token 详情，Northgate 将其显示为
`CACHED_USAGE_MISSING`；因此 1,536 是测得的下界，并不表示缓存结果为零。由于每个语义轮次的
消息或绑定工具都不同，并非相同请求的重放，因此出现 `EXACT_CACHE_BYPASSED` 也符合预期。

## 2026-07-23：北京本地模型协议与整数版本

模型可见的调度契约现在只使用北京本地墙上时钟值，格式为
`YYYY-MM-DDTHH:mm`。UTC 时刻仍保留在 PostgreSQL 和 presentation artifact 中。发送给提供商的
ToolMessages 会丢弃 artifact，旧的绝对时间回执会以防御方式重写，而新的
`dayboard-time-v2` checkpoint namespace 会阻止旧 UTC 回执进入摘要或主模型上下文。时长编辑使用
`new_duration_minutes`，因此模型不再计算结束时间戳。

日历和任务并发控制从 `expected_updated_at` 移至原子整数 `row_version`。为明确本地时间和相邻性
不变量，系统提示词从 772 增至 913 个 token。八个模型可见 schema 从 1,487 降至 1,469 个 token，
固定总量为 2,382 个 token：比上一版本高 5.4%，但仍比初始的 3,717-token 基线低 35.9%。提供商
输入和缓存读取测量仍待部署。

程序化回归覆盖验证了 UTC 存储/本地回执、artifact 隔离、过期版本拒绝、锚点验证，以及将
16:00-17:00 条目缩短为 30 分钟且不移动独立的 17:00 条目。

## 2026-07-23：确定性终止完成

成功的终止调度写入现在会在 Dayboard middleware 中结束 Agent 循环，并使用规范 ToolMessages
组装一段简短、基于事实的完成响应。搜索、错误、部分结果或未解决的工作之后仍会调用模型，但
不再仅仅为了复述 UI 已经渲染的已提交写入而调用模型。固定系统提示词和工具 schema 面仍为
2,382 个 token；这项变更移除了完整的一轮提供商调用，而不是压缩该轮。

变更前的生产样本包含四次最终确认调用，共计 10,144 个提示词 token 和 55 个 completion token。
它们共计 10,199 个 token，占四个 Run 消耗的 34,638 个 token 的 29.4%。在声称已经实现节省前，
仍需记录部署后的提供商测量结果。

## 2026-07-24：v0.3.21 后首个 Admin 缓存样本

Northgate CLI 测量了 Asia/Shanghai 时间 09:00 至 17:01 的 `admin` 流量，并发现了一个与 Run
`79f86d9a-aa4d-40c4-bb54-93bc592f365d` 关联的请求。Dayboard 和 Northgate 均确认只有一次模型
调用：3,954 个提示词 token、6 个 completion token，共计 3,960 个 token。该 Run 没有工具事件、
重试/回退尝试或压缩事件。这确认了之前的多次调用和重复摘要失败在该样本中没有出现。

固定提示词/schema 基线仍为 2,382 个 token，为有界会话/运行时上下文留下约 1,572 个 token。权威
Conversation 包含 134 条较早的持久化消息且没有持久化摘要，但 North checkpoint namespace 提供
有界的运行时状态；持久化消息数量不能证明这 134 条消息全部进入了本次请求。3,954-token 提示词
仍低于 6,000-token 的正常压缩阈值。

提示词缓存读取仍是未知，而不是零。提供商省略了缓存提示词详情，因此 Northgate 报告
`CACHED_USAGE_MISSING`，并将 0% 缓存比例标记为下界。这个单一样本无法证明 32 路稳定
`prompt_cache_key` 分区带来了帮助还是损害。对于语义 Agent 请求，精确响应缓存按预期被绕过。

Northgate 预留了 12,676 个 token，并在结算 3,960 个 token 后释放了 8,716 个 token，估算值与
实际值的比率为 3.201。预留是临时的准入容量，不是提供商 token 消耗。关联元数据存在，但被
归类为 `legacy`；可信动态元数据迁移仍是 Northgate 的独立前置条件。

## 2026-07-27：仅模型系统规则

系统提示词现在只包含必须由模型执行的决策和响应行为。内部冲突检查、PostgreSQL/UTC artifact
所有权、可信上下文注入和底层工具失败处理的描述均已移除。时间分类、北京本地工具输入、序列
引用、变更前搜索、澄清、乐观版本选择和基于事实的确认仍然保留，因为代码无法替模型选择这些
语义。

系统提示词从 913 降至 829 个 `o200k_base` token，提示词减少 9.2%。八个模型可见 schema 仍为
1,469 个 token，因此固定输入从 2,382 降至 2,298 个 token，本步骤减少 3.5%，比初始的
3,717-token 基线减少 38.2%。提供商使用量和语义验收测量仍待部署。

## 2026-07-27：延迟绑定的北京运行时上下文

分钟级北京 datetime、locale 和相对日期表不再位于稳定系统提示词中。Run 创建 Agent 时，Dayboard
会捕获这些内容一次，并在该 Run 的每次模型调用中，将生成的可信 `SystemMessage` 紧接在最新用户
消息之前注入。该上下文不会持久化到会话历史，在同一 Run 的工具轮次之间保持一致，并且会为每条
命令注入，而不是依赖不完整的相对时间关键词检测。

稳定系统提示词为 763 个 `o200k_base` token，从 829 降低而来。对于典型的 `zh-CN` 请求，运行时
上下文约为 67 个 token，因此这次拆分主要改善前缀结构，而不是移除必需的时间上下文。稳定指令
和之前的会话可以形成可复用前缀，而随分钟变化的上下文则保持在当前命令附近。

部署后的 `context-01` Eval 以精确的工具行为通过了创建和上下文重新调度轮次。其冷 Run 通过三次
模型调用使用了 22,189 个输入 token 和 210 个输出 token；Northgate 看到上游在三次调用中都
省略了缓存详情。传播后的第二次 Eval 使用了 22,201 个输入 token 和 215 个输出 token。随后三次
调用都报告了 6,656 个缓存提示词 token，共计 19,968 个缓存 token，精确提示词缓存比例为 89.94%。
按配置的 `$1.00/M` 输入、`$0.10/M` 缓存输入和 `$6.00/M` 输出价格计算，温 Eval 成本为
`$0.005521`；相同使用量若没有提示词缓存，成本约为 `$0.023491`，降低 76.5%。

16:18 的第三次 Eval 跨过了 16:16 温缓存样本的分钟边界，再次通过了两个轮次。Northgate 报告了
一次 6,656-token 缓存读取，并看到提供商在其他两次调用中省略了缓存详情。这证明改变注入的分钟
不再阻止稳定前缀被复用；但由于省略的使用量仍未知，这不能证明每个请求都命中缓存。

与紧邻的上一生产样本相比，部署后的冷输入从 22,669 降至 22,189 个 token，在三次模型调用中
减少 480 个 token，即 2.1%。即使 Northgate 记录了三次缓存命中，Dayboard 的 Eval 事件投影仍将
缓存使用量报告为未知，因此缓存 token 向 Run 事件的传递仍是一个独立的可观测性缺陷。

## 2026-07-27：缓存使用量事件投影

North Runtime 现在会保留来自直接缓存 token 字段，以及来自 LangChain/OpenAI
`input_token_details.cache_read` 和 `prompt_tokens_details.cached_tokens` 形状的提供商缓存读取。
它将规范化后的值作为 `cached_input_tokens` 发出；省略时仍为 `None`，而不是虚构为零。因此
Dayboard 现有的类型化 Run-event 扩展和 Eval 聚合可以直接使用该值，无需第二个提供商专用解析器。

North 回归测试覆盖完整的 `LLMResult -> AIMessage.usage_metadata -> RuntimeJournal` 路径，部署后的
Worker 将合成的 100-input/80-cache 载荷规范化为 `cached_input_tokens=80`。部署后立即进行的两次
生产 Eval 不是正向缓存样本，因为 Northgate 独立确认上游在全部六次调用中都省略了缓存详情。
Dayboard 正确地将这些值保留为未知。未来自然报告的缓存读取必须在 Eval 报告和 Northgate 之间
进行对比，才能完成线上正向路径验证。

## 2026-07-28：v0.3.22 正向缓存与成本基线

部署后的 `context-01` Eval 再次以准确的预期工具通过了创建和上下文重新调度轮次。三次模型调用
使用了 6,336 个输入 token 和 193 个输出 token，共计 6,529 个。每次调用都通过 North 和 Dayboard
报告了提供商缓存详情：4,608 个缓存输入 token，精确提示词缓存比例为 72.73%。Northgate 也从
`prompt_tokens_details.cached_tokens` 独立记录了相同值，并为三次请求计价。

Northgate 收取了 3,348 microdollars，即 `$0.003348`。第一次创建 Run 使用了 2,011 个输入 token
和 58 个输出 token，其中包括 1,536 个缓存输入 token，成本为 `$0.000977`。两次调用的上下文
重新调度 Run 使用了 4,325 个输入 token 和 135 个输出 token，其中包括 3,072 个缓存输入 token，
成本为 `$0.002371`。精确响应缓存仍按预期被绕过；这些是提供商提示词缓存读取，而不是重放的
模型响应。

与之前的温缓存 `context-01` 样本相比，总 token 从 22,416 降至 6,529（`70.9%`），精确成本从
`$0.005521` 降至 `$0.003348`（`39.4%`）。成本降幅小于 token 降幅，是因为之前的样本提示词
缓存比例更高。新的 Eval 预算记录了测得的单次写入基线，并在 `context-01` 首轮超过 2,500 个
总 token 时失败；相对于 2,069-token 结果，仍有约 20.8% 的余量。

## 2026-07-29：v0.3.25 Clarification CAS 基线

部署后的 `same-01` Eval 以 100% 通过了设置、同名选项投影、类型化澄清、状态版本 CAS 提交、
继续操作取消、交互消费，以及最终 scheduled/cancelled REST Oracle 断言。完整的四个 Run 流程在
六次模型调用中使用了 21,315 个输入 token 和 362 个输出 token，共计 21,677 个。

两个 fixture 创建 Run 使用了 2,919 和 3,287 个 token。继续操作取消使用了 4,167 个 token。
澄清 Run 是异常值：三次调用共 11,304 个 token，分别用于搜索、模型决定调用 `ask_clarification`，
以及该工具之后一次不必要的模型调用。仅多余的第三次调用就使用了 3,932 个输入 token 和 49 个
输出 token。六次调用中有三次缺少缓存详情。Northgate 测得至少 6,656 个缓存输入 token，并为
三次调用计价 6,330 microdollars（`$0.006330`）；由于其余三次调用缺少缓存详情和价格结算，
这两个值都是下界。确切的汇总成本仍未知，而不是报告为零。

North 的 `ClarificationMiddleware` 当前会使用 LangGraph `Command` 记录类型化请求，但不会终止
图。[north-agent#1](https://github.com/Notryag/north-agent/issues/1) 现在包含了这项生产证据，
以及一项回归要求：`ask_clarification` 应结束当前 Run，同时不丢失类型化结果。修复后，重新运行
`same-01`，并将模型调用次数、token、延迟和 Northgate 确切成本与此基线进行比较。
